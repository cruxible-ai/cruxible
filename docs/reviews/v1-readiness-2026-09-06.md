## New read-performance lead

A follow-up source audit found a concrete amplification path: [typed batch runtime](../../src/cruxible_core/runtime/playbill_api.py) records consumed paths after each page; [consumption recording](../../src/cruxible_core/playbill/consumption.py) appends a touch per returned Claim into a shared partition. Each [operational-store append](../../src/cruxible_core/playbill/review_operational.py) rereads and verifies prior partition events before its idempotency check and durable write. For N recorded Claims and H retained touches, repeated replay can grow as O(NH + N²), in addition to epoch discovery and page work. This applies when an actor context enables consumption recording.

This is a code-grounded hypothesis for the slow live bulk read, not a measured attribution. Instrument consumption recording separately from Claim evaluation, evidence reads and transport. Consider a bounded batch append only after measuring; retain locking, exact event validation, idempotency and crash behavior. It is a more concrete next performance probe than assuming Claim selection itself is responsible. Selection materializes only the requested page; repeated parsing of admission contracts/types within that page is a secondary candidate.
